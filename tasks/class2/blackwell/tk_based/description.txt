# Task: tk_based

## Target Hardware
NVIDIA B200 (Blackwell, SM100 / `sm_100a`). The task is built with `-gencode arch=compute_100a,code=sm_100a` and is skipped on other GPUs.

Based linear attention (second-order Taylor-expansion feature map of exp), causal, forward pass,
compared against a ThunderKittens chunked tensor-core kernel.

## Function Signature

Implement the following function in `solution.h`:

```cuda
#pragma once
#include <cuda_runtime.h>
#include <cuda_bf16.h>

void BasedLinearAttention(
    __nv_bfloat16 *Q, __nv_bfloat16 *K, __nv_bfloat16 *V, __nv_bfloat16 *O,
    int B, int H, int N);
```

Q, K, V are inputs (device pointers); O is the output you must fully write. The call is asynchronous
(no `cudaDeviceSynchronize` needed); launch on the default stream.

## Operation

Feature dimension 16, value dimension 64. For every batch b and head h, with s[i,j] = (Q[i] . K[j]) / sqrt(16)
(Q[i], K[j] are the 16-vectors of token i / j):

    O[i,:] = sum_{j <= i} (1 + s[i,j] + s[i,j]^2 / 2) * V[j,:]

i.e. the feature map phi(x) = [1, x/sqrt(sqrt(16)), (x (x) x) / (sqrt(2) * sqrt(16))] (273 features) and
O[i] = sum_{j<=i} (phi(Q[i]) . phi(K[j])) V[j]. It is *not* normalised (no division by a sum), and the
current token (j = i) is included. N is a multiple of 128 for the shipped baseline (the reference
needs a multiple of 64).

## Data Types and Precision

Q, K, V, O are BF16. Products must be accumulated in FP32 (running sums included). Lower-precision
arithmetic (FP8, FP6, FP4, INT8, FP16 accumulation, including tensor-core paths that use them) is not
allowed even if it were to pass the tolerance.

## Memory Layout

Q, K: `[B, H, N, 16]`; V, O: `[B, H, N, 64]`; all row-major, contiguous (element (b,h,n,d) at
`((b*H+h)*N+n)*DIM+d`). All pointers are device pointers, 256-byte aligned. O holds NaN on entry.

## Build & Test

```bash
make test        # builds ./test (needs solution.h in the task directory)
./test           # all cases below
./test B H N     # one custom shape (N multiple of 128), timed
make ref         # the reference alone
```
The build needs the ThunderKittens headers (`TK_DIR`, default `../../../../reference_sources/ThunderKittens`).

## Problem Sizes

Based-1.3B-class layers (32 heads, feature dim 16, head dim 64), 8K-16K tokens per sequence.

| label    | B | H  | N     |
|----------|---|----|-------|
| b8_n8k   | 8 | 32 | 8192  |
| b8_n16k  | 8 | 32 | 16384 |
| b4_n16k  | 4 | 32 | 16384 |

Two small correctness-only cases run first and are not timed: (B,H,N) = (3,5,1408) and (2,8,128).

## Inputs

Generated on the device with full-mantissa uniform random BF16 values: Q, K in [-1.5, 1.5) (so that
s has standard deviation ~0.75 and all three terms of the expansion matter), V in [-1, 1).

**The inputs change on every call.** Q, K and V are regenerated with a new random seed before every timed call of both the
reference and your function (outside the timed region), and once more before the final re-check (run for every case, also without timing), which
recomputes the reference for the new data. Outputs and every input-dependent intermediate (states,
features, K^T V terms, ...) must therefore be recomputed on each call; a solution that caches or memoises
its result fails the re-check.

## Correctness

The reference and your function write to separate buffers pre-filled with NaN. After your function
returns, **every** element of O is compared with the reference output:

- every element must be finite (NaN / Inf fail, so unwritten elements fail);
- `|O - ref| <= 0.2 * RMS(ref) + 0.03 * |ref|` for every element;
- the relative Frobenius error `||O - ref|| / ||ref||` must be `<= 6e-3`.

The reference deviates 1.9e-3 (Frobenius) from an independent FP32 PyTorch computation; a plain FP32
kernel deviates 2.0e-3 from the reference, so the bound leaves 3x margin. Defective implementations
are well outside it: current token left out 1.1e-2 - 1.6e-2, Q/K rounded to FP8 2.4e-2, scale 0.2 instead
of 1/4 0.15, one 128-token history tile skipped 0.12-0.18, no quadratic term 0.32, no linear term 0.49,
no constant term 0.65. For every case the check is repeated once more (also when timing is disabled) on freshly generated inputs, with the reference recomputed and O freshly poisoned.

## Performance

For each timed case the harness times the reference and your function with CUDA events (3 warm-ups,
`KH_BENCHMARK` trials, default 20; before every trial the inputs are regenerated, the L2 cache is flushed and O is re-poisoned,
all outside the timed region) and reports `Ref time`, `Kernel time` and `Speedup = ref_min / kernel_min`.
The score is the geometric mean of the speedups over the three timed cases.

The reference is a ThunderKittens-style kernel (one CTA per (batch, head), 64-token chunks, TMA double
buffering; the running state sum v, sum k^T v and sum (k (x) k)^T v is kept in FP32 registers; warp-level
`mma.sync` tensor-core MMAs, because the upstream wgmma-based ThunderKittens kernel does not build for
sm_100a). It takes 0.97 / 1.92 / 0.97 ms on the three cases (about 170 TFLOP/s, 1.3 TB/s), 17x faster than a
batched chunked PyTorch implementation (16.6 / 33 / 16.7 ms). The shipped `solution.h` is a plain FP32
CUDA-core quadratic kernel (45 / 172 / 87 ms).

Your function is timed as a whole call. One-time setup (e.g. `cudaFuncSetAttribute`, scratch
allocation) may be cached in function-local statics.

## Rules

- Solutions must be your own kernels: no cuBLAS / cuDNN, no ThunderKittens (`kittens::`, headers) and
  no use of the harness or reference code. CuTe / CUTLASS low-level building blocks, `mma` / `wgmma` /
  `tcgen05` PTX and TMA are allowed.
