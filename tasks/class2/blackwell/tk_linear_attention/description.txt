# Task: tk_linear_attention

## Target Hardware
NVIDIA B200 (Blackwell, SM100 / `sm_100a`). The task is built with `-gencode arch=compute_100a,code=sm_100a` and is skipped on other GPUs.

Causal linear attention with a per-head exponential decay, forward pass, compared against a
ThunderKittens-style tensor-core reference.

## Function Signature

Implement the following function in `solution.h`:

```cuda
#pragma once
#include <cuda_runtime.h>
#include <cuda_bf16.h>

void LinearAttention(
    __nv_bfloat16 *Q, __nv_bfloat16 *K, __nv_bfloat16 *V, __nv_bfloat16 *O,
    float *slopes,
    int B, int H, int N, int D);
```

Q, K, V, slopes are inputs (device pointers); O is the output you must fully write. The call is
asynchronous (no `cudaDeviceSynchronize` needed); launch on the default stream.

## Operation

For every batch b and head h (s = slopes[h] > 0, i and j are token positions):

    O[b,h,i,:] = sum_{j <= i} exp(-s * (i - j)) * (Q[b,h,i,:] . K[b,h,j,:]) * V[b,h,j,:]

There is no softmax, no normalisation and no scaling of Q.K. Equivalently, with a D x D state
S_i = exp(-s) * S_{i-1} + K_i^T V_i (S_{-1} = 0): O_i = Q_i S_i. The current token (j = i) is included
with weight 1. D is always 128; N is a multiple of 64.

## Data Types and Precision

Q, K, V, O are BF16, slopes is FP32. Products must be accumulated in FP32 and the decay must be
exact (FP32 exp). Lower-precision arithmetic (FP8, FP6, FP4, INT8, FP16 accumulation, including
tensor-core paths that use them) is not allowed even if it were to pass the tolerance.

## Memory Layout

Q, K, V, O: `[B, H, N, D]`, row-major, contiguous (element (b,h,n,d) at `((b*H+h)*N+n)*D+d`).
slopes: `[H]`. All pointers are device pointers, 256-byte aligned. O holds NaN on entry.

## Build & Test

```bash
make test        # builds ./test (needs solution.h in the task directory)
./test           # all cases below
./test B H N     # one custom shape (N multiple of 64), timed
```

## Problem Sizes

Linear-attention layers with 32-64 heads of dimension 128 on one B200: batched 8K / 16K-token prefill
and one 64K-token sequence.

| label      | B | H  | N     |
|------------|---|----|-------|
| b8_n8k     | 8 | 32 | 8192  |
| b4_n16k    | 4 | 64 | 16384 |
| b1_n64k    | 1 | 64 | 65536 |

Two small correctness-only cases (odd batch / head counts, one chunk) run first and are not timed:
(B,H,N) = (3,5,1536) and (2,8,64).

## Inputs

Generated on the device with full-mantissa uniform random BF16 values: Q, K in [-0.153, 0.153),
V in [-1.7, 1.7). slopes[h] = 2^(-8(h+1)/H) * u_h with u_h random in [0.9, 1.1).

**The inputs change on every call.** Q, K and V are regenerated with a new random seed before every
timed call of both the reference and your function (outside the timed region), and once more before the
final re-check, which runs for every case on fresh inputs. The slopes stay fixed across calls. Outputs
and every input-dependent intermediate must therefore be recomputed on each call; a solution that
caches or memoises its result fails the re-check.

## Correctness

The reference and your function write to separate buffers pre-filled with NaN. After your function
returns, **every** element of O is compared with the reference output:

- every element must be finite (NaN / Inf fail, so unwritten elements fail);
- `|O - ref| <= 0.2 * RMS(ref) + 0.03 * |ref|` for every element;
- the relative Frobenius error `||O - ref|| / ||ref||` must be `<= 9e-3`.

## Performance

The reference and your function are timed with CUDA events (3 warm-ups, `KH_BENCHMARK` trials, default
20). Before every trial the inputs are regenerated, the L2 cache is flushed and O is re-poisoned, all
outside the timed region. The harness reports `Speedup = ref_min / kernel_min` per case; the score is
the geometric mean of the speedups over the 3 timed cases.

Your function is timed as a whole call. One-time setup (e.g. `cudaFuncSetAttribute`, scratch
allocation) may be cached in function-local statics. The shipped `solution.h` is a simple correct
baseline that you may replace entirely.

## Rules

- Solutions must be your own kernels: no cuBLAS / cuDNN, no ThunderKittens (`kittens::`, headers) and
  no use of the harness or reference code. CuTe / CUTLASS low-level building blocks, `mma` /
  `tcgen05` PTX and TMA are allowed.
