# Task: 72_blackwell_narrow_precision_gemm

## Target Hardware
NVIDIA B200 (Blackwell, SM100 / `sm_100a`). The task is built with `-gencode arch=compute_100a,code=sm_100a` and is skipped on other GPUs.

NVFP4 x NVFP4 -> BF16 block-scaled GEMM (tcgen05 `kind::mxf4nvf4` block-scaled tensor-core GEMM), compared against a
CUTLASS 3.x/4.x Blackwell block-scaled GEMM.

## Function Signature

Implement the following function in `solution.h`:

```cuda
#pragma once
#include <cstdint>
#include <cuda_runtime.h>
#include <cuda_bf16.h>

cudaError_t BlackwellNvfp4Gemm(
    int M, int N, int K,
    float alpha,                      // product of the two per-tensor (global) FP32 scales
    uint8_t const *A, uint8_t const *SFA,
    uint8_t const *B, uint8_t const *SFB,
    __nv_bfloat16 *D);
```

## Operation

NVFP4 (as produced by NVIDIA's quantizers): every operand is stored as FP4 E2M1 values, one **UE4M3 (FP8 E4M3,
non-negative) scale factor per block of 16 consecutive K elements**, plus one per-tensor FP32 "global scale" that
is folded into `alpha`.

    D[m, n] = bf16( alpha * sum_k  (a[m,k] * sfa[m, k/16]) * (b[n,k] * sfb[n, k/16]) )

where `a`, `b` are the decoded E2M1 values, `sfa`, `sfb` the decoded UE4M3 scales. A is M x K, B is K x N, D is M x N.

## Data Types and Precision

FP4 E2M1 inputs, UE4M3 scales, **FP32 accumulation**, BF16 output (round-to-nearest-even of the FP32 result times
`alpha`). Products of two scaled FP4 values are exact in FP32. Lower-precision arithmetic (rounding the dequantized
operands to FP8, FP16 or BF16 accumulation, power-of-two (UE8M0 / MXFP4-style) scales, 32-element scale blocks, ...) is
not allowed even if it were to pass the tolerance.

## Memory Layouts (exact)

`K` is a multiple of 64 for every tested shape, so no K padding is needed. All pointers are device pointers, 256-byte aligned.

**FP4 data (A and B).** `A` is `uint8_t[M][K/2]` (row-major, `lda = K/2` bytes), `B` is `uint8_t[N][K/2]`
(K-contiguous; equivalently the column-major [K, N] matrix). Byte `j` of row `r` holds the elements `k = 2j` (LOW nibble)
and `k = 2j + 1` (HIGH nibble). A nibble is an E2M1 code: bit 3 = sign, bits 2:0 = magnitude index into
`{0, 0.5, 1, 1.5, 2, 3, 4, 6}` (code 8 is -0). The test data uses all 16 codes uniformly.

**Scale factors (SFA, SFB).** One UE4M3 byte per (row, 16-element K block): scale column `c = k / 16`
(`Kb = K / 16` columns). The decoded value of byte `b` is `(1 + (b & 7)/8) * 2^(((b >> 3) & 15) - 7)` for exponent
field > 0, and `(b & 7) / 512` for exponent field 0 (bit 7 is always 0 here). The bytes are stored in the
cuBLAS / CUTLASS "swizzled 128x4" layout: rows are padded to a multiple of 128 and the scale columns to a multiple of 4
(`Kb_pad = roundup(Kb, 4)`); the buffer has `roundup(rows, 128) * Kb_pad` bytes. The byte of (row `r`, scale
column `c`) lives at

    offset(r, c) = ( (r / 128) * (Kb_pad / 4) + (c / 4) ) * 512  +  (r % 32) * 16  +  ((r / 32) % 4) * 4  +  (c % 4)

i.e. the matrix is cut into 128-row x 4-column tiles (512 bytes each, tiles ordered row-tile-major, then along K), and
inside a tile the byte index is `(r % 32) * 16 + ((r / 32) % 4) * 4 + (c % 4)`. Padding bytes (rows >= `rows`,
columns >= `Kb`) are zero. `SFA` uses `rows = M`, `SFB` uses `rows = N`. This is the same layout as PyTorch's
`SWIZZLE_32_4_4` block-scale layout.

**Output.** `D` is row-major [M, N] BF16 (`ldd = N`). It holds NaN on entry; every element must be written.

## Problem Sizes

The linear layers of Llama-3.1-70B served in NVFP4 on one B200 (hidden 8192, 64 query / 8 KV heads of dimension 128 ->
fused QKV 10240, FFN 28672 -> fused gate+up 57344, vocabulary 128256). A is the activation matrix (M = tokens), B the
quantized weight (N = output features): either an 8K-token prefill chunk or one decode step of 128 sequences.

| label            | M    | N      | K     | layer                        |
|------------------|------|--------|-------|------------------------------|
| decode_mlp_up    | 128  | 57344  | 8192  | fused gate+up projection     |
| decode_mlp_down  | 128  | 8192   | 28672 | FFN down projection          |
| decode_lm_head   | 128  | 128256 | 8192  | LM head                      |
| prefill_qkv      | 8192 | 10240  | 8192  | fused QKV projection         |
| prefill_o_proj   | 8192 | 8192   | 8192  | attention output projection  |
| prefill_mlp_up   | 8192 | 57344  | 8192  | fused gate+up projection     |
| prefill_mlp_down | 8192 | 8192   | 28672 | FFN down projection          |

Two extra correctness-only cases (not timed) check padded scale rows and a K that is not a multiple of the 256-wide
MMA tile: (M=200, N=1152, K=1344) and (M=16, N=2048, K=4096).
`alpha = 0.00731` in every case. Data: uniformly random FP4 codes; scales are random UE4M3 values, log-uniform in
[0.125, 4) with full 3-bit mantissas (never all 1.0).

## Correctness

The CUTLASS reference and your solution write to separate buffers that are pre-filled with NaN. After your function
returns, **every** element of D is compared with the reference output:

- every element must be finite (NaN / Inf fail, so unwritten elements fail);
- `|D - ref| <= 1e-3 * RMS(ref) + 0.03125 * |ref|` for every element (BF16 has 8 significant bits, so one BF16 ulp is
  up to 0.0078 |ref|; 0.03125 leaves 4x margin for the rounding flips that different FP32 summation orders cause);
- the relative Frobenius error `||D - ref|| / ||ref||` must be `<= 3e-4`.

A plain FP32-FMA implementation of the exact dequantized products measures a relative Frobenius error of 3.5e-5 to 9.1e-5
(0 on the smallest shapes), i.e. 3-8x below the bound. Deliberately wrong variants measure: FP16 accumulation 2.0e-3 to
5.0e-3, BF16 accumulation 8e-3 to 3.4e-2, dequantized operands rounded to FP8 3.2e-2, power-of-two scales 0.30,
FP4 magnitudes with the mantissa bit dropped 0.45, scales ignored 0.85, 32-element scale blocks 0.84, linear
(unswizzled) scale layout 1.0-1.2, swapped nibble order 1.4, alpha ignored 136, last 32 K elements skipped 3.4e-2 - 0.15:
all fail on every shape. The check is repeated after the timing loop on a fresh input (see below).

**Inputs change on every call.** Before every timed call of both the reference and your function the harness regenerates the activation matrix A and its scale factors SFA (regenerated with the harness's own random-FP4 / UE4M3 generators; the weights B / SFB stay fixed) with a new random seed (outside the timed region), the first correctness check and the final re-check use their own seeds, and in the final re-check the reference output is recomputed for the new input before your function is called on a freshly poisoned D. Outputs and any input-dependent intermediates must therefore be recomputed on every call; caching them across calls (memoisation) fails the re-check. Only data derived from the fixed operands may be cached.

## Performance

For each shape the harness times the CUTLASS reference and your function with CUDA events (L2 flushed before every trial,
D re-poisoned outside the timed region) and reports `Ref time`, `Kernel time` and `Speedup = ref_min / kernel_min`. The
score is the geometric mean of the speedups over the seven shapes. The reference uses a tile / cluster configuration
tuned per shape (prefill: 256x192 2-SM tile, cluster 2x1; decode: operands swapped so that the 57344 / 8192 / 128256-wide
N dimension fills the MMA, 256x128 tile with cluster 2x1 or 4x1). Against cuBLAS NVFP4 (`torch` `F.scaled_mm`, BlockWise1x16
scales) measured on the same B200 it runs at 106 / 107 / 93 / 88% on the four prefill shapes (qkv / o_proj / mlp_up / mlp_down;
5.7-6.1 PFLOPS dense) and at 136 / 155 / 124% on the three decode shapes (mlp_up / mlp_down / lm_head).

Your function is timed as a whole call, including any host-side launch setup. One-time setup (e.g.
`cudaFuncSetAttribute`, tensor-map creation) may be cached in function-local statics.

## Rules

- Solutions must be your own kernels: no cuBLAS / cuDNN, and no CUTLASS device / kernel / collective GEMM templates.
  CuTe and low-level building blocks (barriers, pipelines, layouts, `tcgen05` PTX) are allowed.
- The shipped `solution.h` is a deliberately simple FP32-FMA SIMT kernel (about 40 TFLOPS, i.e. ~0.5-1% of the reference's speed); it exists to
  validate the harness, a real solution is expected to use `tcgen05.mma ... kind::mxf4nvf4`.
