# Task: 86_blackwell_mixed_dtype_gemm

## Target Hardware
NVIDIA B200 (Blackwell, SM100 / `sm_100a`). The task is built with `-gencode arch=compute_100a,code=sm_100a`.

Weight-only quantized GEMM (W4A16): BF16 activations times INT4 weights with per-group BF16 scales,
BF16 output, compared against the best public implementation for the shape.

## Function Signature

Implement the following function in `solution.h`:

```cuda
#pragma once
#include <cuda_runtime.h>
#include <cuda_bf16.h>
#include <stdint.h>

cudaError_t BlackwellMixedDtypeGemm(
    int M, int N, int K,
    float alpha,
    __nv_bfloat16 const *A, int lda,
    uint8_t const *B, int ldb,
    __nv_bfloat16 const *B_scales, int scale_ldb,
    float beta,
    __nv_bfloat16 *D, int ldd);
```

## Operation

D = alpha * A * dequant(B) + beta * D

with `dequant(B)[k, j] = int4(B[k, j]) * B_scales[j, k / 128]`.
A is M x K, dequant(B) is K x N, D is M x N.

## Data Types and Precision

A, the scales and D are BF16, the weights are signed INT4, accumulation must be FP32 (rounded to BF16
once, at the end). Lower-precision arithmetic (FP8 / FP4 activations or scales, INT8 activation
quantization, FP16 or BF16 accumulation, including tensor-core paths that use them) is not allowed even if
it were to pass the tolerance. Whether the dequantized weight `int4 * scale` is formed exactly in FP32 or
rounded to BF16 (as the reference does) is up to you; both are accepted.

## Memory Layout

- A: **row-major** [M, K] BF16. Element (i, k) at `A[i * lda + k]`, `lda == K`.
- B: **packed INT4, column-major [K, N]** (equivalently [N, K] with K contiguous). Column j occupies K/2
  contiguous bytes starting at `B + j * ldb`, `ldb == K / 2` (in bytes). Element (k, j) is in byte
  `B[j * ldb + k / 2]`: the **low nibble for even k, the high nibble for odd k**, two's complement,
  values in [-8, 7] (all 16 codes occur).
- B_scales: BF16, **row-major [N, K / 128]**: the scale of (k, j) is `B_scales[j * scale_ldb + k / 128]`,
  `scale_ldb == K / 128`. Group size is 128 along K. Scales are random positive BF16 values in [0.004, 0.06).
- D: **row-major** [M, N] BF16, `ldd == N`.

All pointers are device pointers, 256-byte aligned. When `beta == 0`, D holds NaN on entry: you must not
read it (do not compute `0 * D`). K is a multiple of 128 and N a multiple of 8.

## Problem Sizes

The linear layers of Llama-3-70B as weight-only INT4 (hidden 8192, fused QKV 10240, FFN 28672 -> fused
gate+up 57344). M is the number of tokens: decode batches of 1..128 sequences and one 8K-token prefill chunk.

| label               | M    | N     | K     | layer / scenario                         |
|---------------------|------|-------|-------|------------------------------------------|
| decode_m1_mlp_up    | 1    | 57344 | 8192  | single sequence, gate+up projection      |
| decode_m16_qkv      | 16   | 10240 | 8192  | 16 sequences, fused QKV                  |
| decode_m64_mlp_down | 64   | 8192  | 28672 | 64 sequences, FFN down projection        |
| decode_m128_o_proj  | 128  | 8192  | 8192  | 128 sequences, attention output          |
| decode_m128_mlp_up  | 128  | 57344 | 8192  | 128 sequences, gate+up projection        |
| prefill_qkv         | 8192 | 10240 | 8192  | 8K-token prefill chunk, fused QKV        |

All shapes use `alpha = 1, beta = 0`. One extra correctness-only case (M=48, N=1280, K=8192,
`alpha = 0.75`, `beta = 0.5`, D initialised with random BF16 data) checks alpha / beta; it is not timed.
A is uniform random BF16 in [-1, 1) with full mantissas.

## Correctness

The reference and your solution write to separate buffers that are pre-filled with NaN (for
`beta != 0`: with the same random D). After your function returns, **every** element of D is compared
with the reference output:

- every element must be finite (NaN / Inf fail, so unwritten elements fail);
- `|D - ref| <= 6e-2 * RMS(ref) + 1.6e-2 * |ref|` for every element, and the relative Frobenius error
  `||D - ref|| / ||ref||` must be `<= 7.5e-3`.

**Inputs change on every call.** The activations A are refreshed with new random values before every
timed call of both the reference and your function (outside the timed region), so outputs and any
input-dependent intermediate must be recomputed on every call; memoizing results does not work. After
the timing loop the harness refreshes A once more, recomputes the reference, re-poisons D and calls your
function again; that final check on fresh inputs must pass too (it runs for every case). The weights
and scales stay fixed.

## Performance

For each shape the harness times the reference and your function with CUDA events (the L2 cache is
flushed before every trial; D is re-poisoned outside the timed region) and reports `Ref time`,
`Kernel time` and `Speedup = ref_min / kernel_min`. The score is the geometric mean of the speedups
over the six shapes.

Your function is timed as a whole call, including any host-side launch setup. One-time setup (e.g.
`cudaFuncSetAttribute`, tensor-map creation) may be cached in function-local statics. The shipped
`solution.h` is a simple correct baseline that you may replace entirely.

**Weight repacking (fairness rule).** The references need the weights in their own kernel-specific layouts. The harness hands
every implementation the plain layout documented above; the references convert it **once, outside the timed region**
(what an inference engine does at model-load time), so their timed work is the GEMM kernel launches only. You may do
the same: repack / transpose / pre-convert `B` and `B_scales` once into a function-local static cache keyed on the
weight pointers and (N, K), on the first (warm-up) call, and reuse it. Everything that depends on A, alpha, beta or D
must be recomputed on every call. The weights are constant across calls (a buffer address and shape always carry
identical contents), so the first-call repack cost is not measured; a per-call dequantization pass that writes a dequantized copy
of the weights to memory is real per-call work and is not allowed to be hidden this way (see Rules).

## Rules

- Solutions must be your own kernels: no cuBLAS / cuDNN, and no CUTLASS device / kernel / collective GEMM
  templates. CuTe and low-level building blocks (barriers, pipelines, layouts, `tcgen05` PTX) are allowed.
- The steady-state per-call kernel must read the INT4 weights (the packed bytes or a one-time repacked copy of the same
  4-bit data, about N*K/2 bytes), not a dequantized 8/16-bit copy of the weights; the activations stay BF16.
