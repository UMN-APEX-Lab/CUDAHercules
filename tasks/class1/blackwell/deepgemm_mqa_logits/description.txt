# Task: deepgemm_mqa_logits

## Target Hardware
NVIDIA B200 (Blackwell, SM100 / `sm_100a`). The task is built with `-gencode arch=compute_100a,code=sm_100a` and is skipped on other GPUs. The reference kernel is compiled for the 148 SMs of a B200.

FP8 multi-query-attention scoring: the "lightning indexer" logits of DeepSeek-V3.2 (64 indexer heads of dimension 128 against a single shared key per token), compared against DeepGEMM's SM100 `fp8_fp4_mqa_logits` kernel (tcgen05 block-scaled UMMA, DeepSeek, MIT license).

This is NOT softmax attention: every (query, key) pair gets one scalar logit

    logits[i, j] = sum_h  w[i, h] * relu( dot_mx(Q[i, h, :], KV[ks[i] + j, :]) )          0 <= j < ke[i] - ks[i]

where `dot_mx` is the MXFP8 block-scaled dot product (E4M3 values, one UE8M0 scale per block of 32 head-dim elements):

    dot_mx(q, k) = sum_{b=0..3}  2^(sfq[b] - 127) * 2^(sfk[b] - 127) * sum_{d in [32b, 32b+32)} q[d] * k[d]

## Function Signature

Implement in `solution.h`:

```cuda
#pragma once
#include <cuda_runtime.h>
#include <cuda_fp8.h>
#include <cuda_bf16.h>
#include <stdint.h>

cudaError_t solution_mqa_logits(
    const __nv_fp8_e4m3 *q,        // [seq_len, num_heads, head_dim]
    const uint32_t *q_sf,          // [seq_len, num_heads]      4 packed UE8M0 scales
    const __nv_fp8_e4m3 *kv,       // [seq_len_kv, head_dim]
    const uint32_t *kv_sf,         // [seq_len_kv]              4 packed UE8M0 scales
    const __nv_bfloat16 *weights,  // [seq_len, num_heads], row stride weights_stride (elements)
    int weights_stride,
    const int *cu_seq_len_k_start, // [seq_len]
    const int *cu_seq_len_k_end,   // [seq_len]
    __nv_bfloat16 *logits,         // [seq_len, logits_stride], compressed (see below)
    int logits_stride,
    int seq_len, int seq_len_kv, int num_heads, int head_dim,
    cudaStream_t stream);
```

`num_heads` = 64 and `head_dim` = 128 in all tests.

## Data Layout

- `q`: row-major `[seq_len, num_heads, head_dim]` E4M3, element (i, h, d) at `(i * num_heads + h) * head_dim + d`.
- `q_sf`: `[seq_len, num_heads]` uint32. Byte b (bits 8b..8b+7, little endian) is the UE8M0 exponent of the scale of q[i, h, 32b .. 32b+31]: scale = 2^(byte - 127). Test values are in [124, 131] (scales 2^-3 .. 2^4).
- `kv`: row-major `[seq_len_kv, head_dim]` E4M3 (one key head shared by all query heads); `kv_sf`: `[seq_len_kv]` uint32, same byte convention (the array is padded to a multiple of 4 entries).
- `weights`: BF16 `[seq_len, num_heads]`, row stride `weights_stride` = 64 elements.
- `cu_seq_len_k_start/end`: row i attends to the KV tokens `[ks[i], ke[i])`, `0 <= ks[i] <= ke[i] <= seq_len_kv`. An empty range is allowed.
- `logits`: BF16, row stride `logits_stride` (a multiple of 512, at least the longest range), `align(seq_len, 2)` rows allocated. **Compressed layout**: `logits[i * logits_stride + j]` holds the logit of KV token `ks[i] + j`, for `0 <= j < ke[i] - ks[i]`.

Only that region is defined and checked. Everything else in the buffer (the rest of each row, padding) is "don't care": it is NaN on entry and never looked at, so do not rely on it and do not spend time on it. All pointers are device pointers, 256-byte aligned.

## Correctness

The DeepGEMM reference and your function read the same inputs and write to separate buffers that are pre-filled with NaN. After your function returns, **every** element of the defined region (see above) is compared with the reference:

- every element must be finite (NaN / Inf fail, so unwritten elements fail);
- `|x - ref| <= 0.4 * RMS(ref) + 0.03 * |ref|` for every element, and the relative Frobenius error `||x - ref|| / ||ref|| <= 1.5e-2` (RMS and norms over the defined region).

Calibration (measured on B200): the DeepGEMM kernel reduces the 64 heads in BF16 arithmetic and stores BF16, so it is itself 4.7e-3 (Frobenius) away from an exact FP64 evaluation of the same quantized inputs; an exact FP32 implementation differs from it by 5.0e-3 (max element error 0.12 RMS), so the bounds are 3x above a correct kernel. They are far below the error of the wrong variants we tried: Q or KV rounded to FP4 (0.25), one head of 64 skipped (0.125), scale factors ignored (0.9), a wrong UE8M0 bias (0.75), ReLU missing or applied after the weights (1.0), weights ignored (6), ks ignored or off by one (> 1 / NaN), a tile or half of the columns unwritten (NaN). The check is repeated once more at the end on freshly regenerated inputs (new seed): the reference output is recomputed for them, your output is re-poisoned, and your function must produce the right answer for the new inputs.

## Performance

For each case the harness times the DeepGEMM reference and your function with CUDA events (the L2 cache is flushed before every trial; the output is re-poisoned outside the timed region) and reports `Ref time`, `Kernel time` and `Speedup = ref_min / kernel_min`. The score is the geometric mean of the speedups over the five cases. The reference is launched with DeepGEMM's own host parameters (tensor maps and function attributes built once outside the timed region; the persistent grid-stride schedule, which was faster than the scheduling-metadata variant in every case including the metadata kernel). It reaches 2.6 - 2.9 PFLOPS of FP8 tensor-core work (1.1 PFLOPS on the small packed-docs case) against the 4.5 PFLOPS dense FP8 peak.

**The inputs change on every call.** Before every timed call of the reference and of your function (outside the timed region) the harness regenerates Q, its MX scale factors `q_sf` and the weights (KV, the key cache, stays fixed) with a new seed; the first correctness check and the final re-check use their own seeds as well. Outputs and input-dependent intermediates must therefore be recomputed on every call; caching or memoising results across calls produces wrong answers and fails the final check.

Your function is timed as a whole call, including host-side launch setup. One-time setup (e.g. `cudaFuncSetAttribute`, tensor-map creation) may be cached in function-local statics.

## Rules

- Solutions must be your own kernels: no cuBLAS / cuDNN, no CUTLASS device / kernel / collective templates, and in particular no use of DeepGEMM (`deep_gemm` headers / namespaces, its SM100 MQA-logits kernel and scheduler) -- including it is rejected. CuTe and low-level building blocks (barriers, pipelines, layouts, `tcgen05` PTX, TMA) are allowed.
- Do not re-quantize Q / KV to narrower formats (FP4 / FP6 / INT8). FP16 accumulation PTX is rejected (it cannot be distinguished from the reference's own BF16 reduction error by the tolerance).
