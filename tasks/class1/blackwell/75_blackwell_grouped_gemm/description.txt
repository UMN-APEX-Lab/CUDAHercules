# Task: 75_blackwell_grouped_gemm

## Target Hardware
NVIDIA B200 (Blackwell, SM100 / `sm_100a`). The task is built with `-gencode arch=compute_100a,code=sm_100a` and is skipped on other GPUs.

Pointer-array grouped GEMM (BF16 in, FP32 accumulation, BF16 out) on the expert GEMMs of a Qwen3-30B-A3B
mixture-of-experts layer, compared against the CUTLASS 3.x Blackwell grouped GEMM (example 75).
The groups are **uneven**: the number of rows per group follows a skewed router, and some groups are empty.

## Function Signature

Implement the following function in `solution.h`:

```cuda
#pragma once
#include <cuda_runtime.h>
#include <cuda_bf16.h>

cudaError_t BlackwellGroupedGemm(
    int num_groups,
    int const *Ms, int const *Ns, int const *Ks,                // device arrays [num_groups]
    __nv_bfloat16 const *const *A_ptrs, int const *ldas,        // device arrays [num_groups]
    __nv_bfloat16 const *const *B_ptrs, int const *ldbs,
    __nv_bfloat16 *const *D_ptrs, int const *ldds);
```

All group tables (`Ms`, `Ns`, `Ks`, pointers, leading dimensions) are **device** arrays; a solution
that needs them on the host has to copy them (and pays for that in the timing), exactly as for a
GPU-side router.

## Operation

For every group g:  `D_g = A_g * B_g`   (A_g is M_g x K_g, B_g is K_g x N_g, D_g is M_g x N_g).

- `M_g` is arbitrary and may be **0** (an expert that received no token): nothing is read or written
  for such a group. `N_g` and `K_g` are multiples of 64 and may differ between groups (one test mixes
  two layer shapes in one launch).
- Group sizes are not equal and are not multiples of any tile size; empty groups exist.

## Data Types and Precision

A and B are BF16, D is BF16. Products must be accumulated in FP32 and rounded to BF16 once, at the end.
Lower-precision arithmetic (FP8, FP6, FP4, INT8, or FP16 accumulation, including tensor-core paths that
use them) is not allowed even if it were to pass the tolerance.

## Memory Layout

- A_g: **row-major** [M_g, K_g] (the routed token rows of expert g). Element (i, k) at `A_g[i * lda + k]`, `lda == K_g`.
- B_g: **column-major** [K_g, N_g] (equivalently the nn.Linear weight, row-major [N_g, K_g]). Element (k, j) at `B_g[k + j * ldb]`, `ldb == K_g`.
- D_g: **row-major** [M_g, N_g]. Element (i, j) at `D_g[i * ldd + j]`, `ldd == N_g`.

In the tests the A_g of all groups of one layer are consecutive row ranges of one token matrix
(sorted by expert), the B_g are slices of one stacked weight tensor [E, N, K], and the D_g are consecutive
row ranges of one output matrix. All pointers are 256-byte aligned for the first group and 16-byte
aligned for every group. The D buffers hold NaN on entry: every element of every non-empty group
must be written.

## Problem Sizes

Qwen3-30B-A3B: 128 experts, top-8 routing, hidden size 2048, expert FFN size 768. The fused
gate+up projection is [rows, 2048] x [2048 -> 1536], the down projection [rows, 768] x [768 -> 2048].
Each token picks 8 distinct experts; the router has Zipf-skewed expert popularity (random expert
order) and a number of experts that never fire; the routing is deterministic. `rows` is the number
of routed token rows, tokens x 8.

| label              | groups (empty) | rows total | N    | K    | rows per group (min / mean / max) | scenario                              |
|--------------------|----------------|-----------:|-----:|-----:|-----------------------------------|---------------------------------------|
| prefill8k_gate_up  | 128 (8)        | 65536      | 1536 | 2048 | 0 / 512 / 6299                    | 8K-token prefill chunk                |
| prefill8k_down     | 128 (8)        | 65536      | 2048 | 768  | 0 / 512 / 6299                    | same chunk, down projection           |
| prefill2k_gate_up  | 128 (12)       | 16384      | 1536 | 2048 | 0 / 128 / 1910                    | 2K-token chunk                        |
| prefill2k_down     | 128 (12)       | 16384      | 2048 | 768  | 0 / 128 / 1910                    | 2K-token chunk, down projection       |
| overlap_mixed_nk   | 256 (24)       | 32768      | 1536 / 2048 | 2048 / 768 | 0 / 128 / 1880          | two micro-batches overlapped: the gate+up GEMMs of one and the down GEMMs of the other in one launch |

Inputs are uniform random BF16 values in [-1, 1) with full mantissas.

## Correctness

The CUTLASS reference and your solution write to separate buffers that are pre-filled with NaN.
After your function returns, **every** output element (all groups, including the ragged tails of every
group) is compared with the reference, per layer (for `overlap_mixed_nk` per layer shape):

- every element must be finite (NaN / Inf fail, so unwritten elements fail);
- `|D - ref| <= 1e-2 * RMS(ref) + |ref| / 128` for every element (the second term is one BF16 ulp, so a
  last-bit difference in the BF16 rounding is accepted);
- the relative Frobenius error `||D - ref|| / ||ref||` must be `<= 5e-4`.

**The token matrix changes on every call.** The A operands (token rows) are regenerated with a new random
seed outside the timed region before every timed call of the reference and of your function, and the final
re-check, which runs on fresh inputs for every case, recomputes the reference for them. Outputs and any
input-dependent intermediate must therefore be recomputed on every call. The expert weights (B) and the
group tables stay fixed.

## Performance

For each scenario the harness times the reference and your function with CUDA events (the L2 cache is
flushed before every trial; the outputs are re-poisoned outside the timed region). The score is the
geometric mean of the per-scenario speedups `ref_min / kernel_min` over the seven scenarios.

Your function is timed as a whole call, including any host-side launch setup and any copy of the group
tables; the reference's group tables are prepared outside the timed region. One-time setup (e.g.
`cudaFuncSetAttribute`, tensor-map creation) may be cached in function-local statics.

## Rules

- Solutions must be your own kernels: no cuBLAS / cuDNN, and no CUTLASS device / kernel / collective
  GEMM templates. CuTe and low-level building blocks (barriers, pipelines, layouts, `tcgen05` PTX) are
  allowed.
