# Task: 92_blackwell_moe_gemm

## Target Hardware
NVIDIA B200 (Blackwell, SM100 / `sm_100a`). The task is built with `-gencode arch=compute_100a,code=sm_100a` and is skipped on other GPUs.

Uneven-token Mixture-of-Experts grouped GEMM with **DeepSeek-V3 FP8 block scaling** (FP8 E4M3 in,
FP32 accumulation, BF16 out) on the routed-expert GEMMs of a DeepSeek-V3 MoE layer, compared against the
CUTLASS 3.x Blackwell grouped (pointer-array) blockwise-scaled GEMM (example 81). The routed tokens arrive
the way a token dispatcher delivers them: sorted by expert, with per-expert counts / offsets on the
device. The number of tokens per expert is **uneven** (a skewed router) and some experts receive **no**
token.

## Function Signature

Implement the following function in `solution.h`:

```cuda
#pragma once
#include <cuda_runtime.h>
#include <cuda_fp8.h>
#include <cuda_bf16.h>

cudaError_t BlackwellMoeGemm(
    int num_experts, int total_rows, int N, int K,
    __nv_fp8_e4m3 const *X,          // [total_rows, K]               row-major, rows sorted by expert
    float const *X_scale,            // [total_rows, K/128]           row-major (K/128 scales of a row contiguous)
    __nv_fp8_e4m3 const *W,          // [num_experts, N, K]           row-major (K contiguous)
    float const *W_scale,            // [num_experts, N/128, K/128]   row-major (K/128 contiguous)
    int const *expert_offsets,       // [num_experts + 1]             device array, offsets[0] = 0, offsets[E] = total_rows
    int const *tokens_per_expert,    // [num_experts]                 device array, = offsets[e+1] - offsets[e]
    __nv_bfloat16 *Y);               // [total_rows, N]               row-major
```

`total_rows`, `num_experts`, `N`, `K` are host values (the dispatcher knows the number of routed rows, e.g.
tokens x top-k); the per-expert split is only available on the **device**. A solution that wants it on the
host has to copy it (and pays for that in the timing), exactly as in a GPU-side dispatcher.

## Quantisation scheme (DeepSeek-V3)

- **Activations X**: FP8 E4M3 values with one FP32 scale per **token** and per **128 channels of K**
  (1x128 blocks, the output of a per-token-group quantiser). `X_scale[r, kb]` belongs to
  `X[r, 128*kb .. 128*kb+127]`; element address `X_scale[r * (K/128) + kb]`. The scale table is aligned
  with the expert-sorted rows of X (row r of X and row r of X_scale are the same token).
- **Weights W**: FP8 E4M3 values with one FP32 scale per **128 x 128 block** (N x K) of each expert
  (the checkpoint's `weight_scale_inv`). `W_scale[e, nb, kb]` belongs to `W[e, 128*nb .. 128*nb+127,
  128*kb .. 128*kb+127]`; element address `W_scale[(e * (N/128) + nb) * (K/128) + kb]`. Every expert has
  its own table.
- Scales multiply the FP8 values (dequantised value = fp8 value x scale). Scales are random positive FP32
  with full mantissas: activation scales uniform in [2e-3, 2e-2), weight scales uniform in [1e-4, 1e-3);
  the FP8 values use the whole E4M3 range (uniform in [-448, 448) rounded to FP8).

## Operation

For every expert e and every row r in `[expert_offsets[e], expert_offsets[e+1])`, n in [0, N):

    Y[r, n] = sum_{kb = 0}^{K/128 - 1}  X_scale[r, kb] * W_scale[e, n/128, kb]
                  * ( sum_{k = 128 kb}^{128 kb + 127}  X[r, k] * W[e, n, k] )

The FP8 x FP8 products of a 128-wide K block are accumulated in FP32, multiplied by that block's two
scales and added to the FP32 result; the result is rounded to BF16 once. Experts with zero rows own no
rows: nothing is read or written for them. `K` and `N` are multiples of 128; the row ranges are arbitrary
(not multiples of any tile size, not padded, not equal); empty experts exist.

## Data Types and Precision

X and W are FP8 E4M3, the scales are FP32, Y is BF16. Products must be accumulated in FP32 and the block
scales applied in FP32. Lower-precision arithmetic (FP6, FP4, INT8, or FP16 accumulation, including
tensor-core paths that use them) is not allowed even if it were to pass the tolerance.

## Memory Layout

All pointers are device pointers, 256-byte aligned; the row ranges of the experts start at arbitrary row
indices (so the per-expert start addresses are multiples of K bytes for X, of 4K/128 bytes for X_scale
and of 2N bytes for Y). Y holds NaN on entry: every element of every non-empty expert's rows must be
written.

## Problem Sizes

DeepSeek-V3: 256 routed experts, top-8 routing, hidden size 7168, expert FFN size 2048. The fused gate+up
projection is [rows, 7168] x [7168 -> 4096], the down projection [rows, 2048] x [2048 -> 7168]. Each token
picks 8 distinct experts from a router with Zipf-skewed popularity (random expert order) and some experts
that never fire; the routing is deterministic. The expert-parallel scenario is a shard of 32 local experts
that receives 16K dispatched token rows.

## Correctness

The CUTLASS reference and your solution write to separate buffers that are pre-filled with NaN.
After your function returns, **every** element of Y (all rows of all experts) is compared with the
reference:

- every element must be finite (NaN / Inf fail, so unwritten rows fail);
- `|Y - ref| <= 1e-2 * RMS(ref) + |ref| / 128` for every element (the second term is one BF16 ulp, so a
  last-bit difference in the BF16 rounding is accepted);
- the relative Frobenius error `||Y - ref|| / ||ref||` must be `<= 1e-4`.

**The activations change on every call.** X (the FP8 data) and X_scale are regenerated with a new random seed
outside the timed region before every timed call of the reference and of your function, and the final
re-check, which runs on fresh inputs for every case, recomputes the reference for them. Outputs and any
input-dependent intermediate must therefore be recomputed on every call. The expert weights, weight scales
and the routing offsets / counts stay fixed for a given size.

## Performance

For each scenario the harness times the reference and your function with CUDA events (the L2 cache is
flushed before every trial; Y is re-poisoned outside the timed region). The score is the geometric mean of
the per-scenario speedups `ref_min / kernel_min` over the seven scenarios.

CUTLASS has no ragged-contiguous blockwise variant, so the reference treats the experts as groups; the
small device kernel that builds its group tables from `expert_offsets` / `tokens_per_expert` is part of
every timed reference call. Your function is timed as a whole call, including any host-side launch setup
and any copy of the per-expert counts. One-time setup (e.g. `cudaFuncSetAttribute`, tensor-map creation)
may be cached in function-local statics.
